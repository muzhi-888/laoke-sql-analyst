# 04 · 常见反模式与陷阱

> 这些写法「能跑但迟早出事」，本 Skill 的 `sql_lint.py` 已内置静态扫描。本文件讲为什么错、怎么改。

## 一、SELECT *（WARN）

- 问题：多表 JOIN 时列名冲突；返回无用列浪费 IO/带宽；表结构变更易 break 下游。
- 改法：显式列清单。本 Skill 扫到即 WARN。

## 二、DELETE / UPDATE 无 WHERE（ERROR，最危险）

- 问题：删/改全表，生产事故第一来源。
- 改法：先 `SELECT` 看影响行数，再补 `WHERE`；大表用事务 + 限量。
- 本 Skill 扫到即 ERROR，且会在报告里反复提醒。

## 三、笛卡尔积（WARN）

- 写法：`FROM a, b` 没 ON 也没 WHERE。
- 问题：行数 = a×b，瞬间爆量。
- 改法：显式 `JOIN ... ON`。本 Skill 检测逗号连接且无条件即 WARN。

## 四、SQL 注入（ERROR/WARN）

- 写法：字符串拼接用户输入 `'...' + user_input + '...'`、永真式 `OR 1=1`。
- 问题：攻击者读库/删库/绕过鉴权。
- 改法：参数化查询（`?` / `%(name)s` / 预编译语句），永远不拼用户输入进 SQL 字符串。
- 本 Skill 扫到拼接或 `OR 1=1` 即报警。

## 五、N+1 查询

- 写法：先查 100 个用户，再循环 100 次各查其订单。
- 问题：101 次往返，慢。
- 改法：一次 `JOIN` 或 `IN (...)` 批量取；或用 ORM 的 eager loading。

## 六、隐式类型转换

- 写法：`WHERE phone = '13800000000'`（phone 是 BIGINT）。
- 问题：索引失效，全表扫描；某些库直接报错。
- 改法：传入与列同类型的值，或建函数索引。

## 七、前导通配符 LIKE '%x'

- 写法：`WHERE name LIKE '%明'`。
- 问题：无法用索引，扫全表。
- 改法：后缀匹配 `LIKE '张%'` 能用索引；中间匹配考虑全文索引/倒排。

## 八、在列上套函数

- 写法：`WHERE DATE(created) = '2026-09-08'`。
- 问题：索引失效。
- 改法：`WHERE created >= '2026-09-08' AND created < '2026-09-09'`。

## 九、NULL 误用

- `NULL` 不等于任何值，包括自己：`WHERE col = NULL` 永远不成立，要用 `IS NULL`。
- `NULL` 参与运算结果还是 `NULL`，聚合时注意 `COUNT(*)` vs `COUNT(col)` 差异。

## 十、深分页 OFFSET 大数

- `LIMIT 100000, 20` 扫 10 万行。改游标分页（见 references/02 第六节）。

## 速查口诀

> 不写 `*`、删改必带 `WHERE`、JOIN 必有 `ON`、用户入参必参数化、类型对齐再比较、函数别套列上。
