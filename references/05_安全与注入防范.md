# 05 · 安全与注入防范：SQL 的生死线

> SQL 注入是 Web 安全头号漏洞（OWASP Top 10 常驻）。本文件给可落地的防范清单，配合本 Skill 的静态扫描。

## 一、注入原理（一句话）

把「用户输入」当「代码」执行了。例如：
```sql
-- 拼接： "SELECT * FROM users WHERE name = '" + name + "'"
-- 用户输 name = ' OR '1'='1   → 变成
SELECT * FROM users WHERE name = '' OR '1'='1'   -- 恒真，拖出全表
```
更狠的：`' ; DROP TABLE users; --` 直接删库。

## 二、根治：参数化查询（唯一正解）

所有语言都支持，绝不拼字符串：

```python
# Python (DB-API)
cur.execute("SELECT * FROM users WHERE name = %s AND age > %s", (name, age))
```
```java
// JDBC 预编译
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, name);
```
```sql
-- PostgreSQL 服务端预备语句
PREPARE stmt(text) AS SELECT * FROM users WHERE name = $1;
EXECUTE stmt('alice');
```
- 占位符让用户输入永远被当「数据」，不被当「代码」。
- 本 Skill 的 `INJECTION_CONCAT` 规则就是扫「字符串拼接」痕迹，提醒你换参数化。

## 三、最小权限原则

- 应用账号只给「必要的库表 + 必要的增删改查」，绝不给 DROP/GRANT/文件权限。
- 读接口用只读账号，写接口用受限账号。
- 即便被注入，权限越小损失越小。

## 四、输入校验（纵深防御，非替代参数化）

- 白名单：枚举值（status IN ('paid','unpaid')）直接校验。
- 类型强转：数字/日期参数先转类型再传，非法直接拒。
- 长度限制：用户名最长 50，防超长 payload。
- 转义仅作兜底，不能作为主防线（不同库转义规则不同，易漏）。

## 五、ORM 不是万能盾

- 多数 ORM 默认参数化，但：
  - 原生 SQL 片段（`raw()`/`execute()`）仍可能注入。
  - 字符串拼进 ORM 查询同样危险。
- 本 Skill 建议：用 ORM 但凡写原生 SQL 必过 `sql_lint.py` 的注入扫描。

## 六、脱敏与审计

- 返回给前端的数据脱敏：手机号中间四位、身份证隐藏。
- 敏感操作留审计日志：谁、何时、改了什么。
- 错误回显不要暴露 SQL 原文（防信息泄露）。

## 七、上线前安全 checklist

- [ ] 所有外部输入走参数化 / 预编译
- [ ] 应用 DB 账号最小权限
- [ ] 不存在字符串拼接 SQL
- [ ] 跑了本 Skill 的 `sql_lint.py`，无 INJECTION_* 告警
- [ ] 错误回显不泄露 SQL / 表结构
- [ ] 敏感数据有脱敏与审计

## 八、本 Skill 的注入扫描覆盖

`sql_lint.py` 检测：
- `INJECTION_TAUTOLOGY`：OR 1=1 等永真式（ERROR）
- `INJECTION_CONCAT`：字符串 `+`/`||` 拼接（WARN）
- `INJECTION_COMMENT`：引号后 `--` 截断（INFO）

三者同时出现 = 高度疑似注入，必须人工复核来源可信度。
