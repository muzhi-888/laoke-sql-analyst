# 02 · 查询优化基础：让慢查询快起来

> 很多人写 SQL 只求「能出数」，上线后被慢查询拖垮。本文件讲最实用的优化常识，不用懂底层也能避坑。

## 一、为什么慢？先看执行计划

- 任何慢查询第一步：`EXPLAIN`（MySQL/PG）/ `EXPLAIN PLAN`（Oracle）/ `SET SHOWPLAN`（SQL Server）。
- 重点看：是否 `ALL`（全表扫描）、`rows` 预估行数、`type` 是否 `range`/`ref` 而非 `ALL`。
- 本 Skill 的 `sql_lint.py` 不替你跑 EXPLAIN，但能拦住「无 WHERE 全表操作」这类最蠢的慢+危险写法。

## 二、索引：加速的本质

- 索引像书的目录，让数据库不用翻完全本。
- 哪里建：高频 `WHERE`、`JOIN ON`、`ORDER BY`、`GROUP BY` 的列。
- 复合索引遵循「最左前缀」：`INDEX(a,b,c)` 能加速 `(a)`、`(a,b)`、`(a,b,c)`，但不能加速只查 `(b)`。
- 别乱建：索引占空间、拖慢写入；写多读少的表索引要克制。
- 失效场景：对列做函数/运算（`WHERE YEAR(created)=2026` → 索引失效，改成 `created >= '2026-01-01'`）。

## 三、避免全表扫描的习惯

| 反模式 | 正解 |
|---|---|
| `SELECT *` | 只取要的列，减少 IO 与列冲突 |
| `WHERE func(col)=x` | 改成范围/等值，保留索引 |
| `LIKE '%关键词%'` | 前导通配符必扫全表，考虑全文索引 |
| 无 LIMIT 的探索查询 | 加 `LIMIT 100` 防爆量 |
| 隐式类型转换 | `WHERE id='123'`（id 是 int）→ 转 int 失败扫全表，传数字 |

## 四、JOIN 优化

- 小表驱动大表：多数优化器会自动选，但写的时候把过滤条件尽量下推到各表 `WHERE`，别等 JOIN 后过滤。
- 笛卡尔积（`FROM a, b` 无 ON/WHERE）是性能灾难，本 Skill 会 WARN。
- JOIN 字段类型/字符集不一致 → 无法用索引，务必对齐。

## 五、减少回表与临时表

- 覆盖索引：查询列都在索引里，不用回表。
- `GROUP BY` / `DISTINCT` / `ORDER BY` 易触发临时表，数据量大时慢；看执行计划是否 `Using temporary`。
- 子查询改 JOIN 或 CTE，很多时候更快更清晰。

## 六、分页深翻页陷阱

`LIMIT 100000, 20` 要扫 10 万行再丢。改进：
```sql
-- 游标分页：记住上一页最后 id
SELECT * FROM orders WHERE id > :last_id ORDER BY id LIMIT 20;
```

## 七、优化 checklist

- [ ] 跑了 EXPLAIN，没有全表扫描
- [ ] WHERE/JOIN 列有索引且未被函数破坏
- [ ] 没用 SELECT *
- [ ] 加了 LIMIT（探索查询）
- [ ] 深分页用了游标而非 OFFSET 大数
- [ ] 数据量大的聚合有合适索引支撑
